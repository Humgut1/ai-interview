# Screen V1 로드맵 (README 7·8단계)

2026-09-24 정리. 화면(1~6단계)은 이미 있다. 이 문서는 **남은 7단계(채점·후속 질문 AI)와 8단계(저장)** 를 어디까지 하면 V1 인지와 순서만 정한다. 이 순서 밖의 기능은 V1 이 끝난 뒤에 논의한다.

## V1 문장

> Hire 에서 AI 1차 면접을 보내기로 한 후보자가 링크로 채팅 면접을 마치면, Screen 이 평가 기준대로 **문항별 점수와 근거가 된 답변 원문**을 서버에 남기고, 담당자는 TalentCore 계정으로 들어가 검토한 결과를 **Hire 후보자 상세**에서 본다. 합격·불합격은 언제나 사람이 Hire 에서 정한다.

## 누가 무엇을 갖나 (제품 소유권)

| 무엇 | 주인 | 이유 |
| --- | --- | --- |
| 계정·로그인 | **Core** | Hire·Grow 와 같은 TalentCore 계정(SSO). Screen 에 계정 표를 따로 만들지 않는다. |
| 후보자·전형 단계·합불 판정 | **Hire** | 후보자는 Hire 에 있다. Screen 은 판정 버튼을 갖지 않는다. |
| 평가 기준(rubric)·면접 대화·AI 점수·담당자 검토 | **Screen** | 면접 자체는 Screen 것. Hire 는 요약만 읽어 간다. |

연결 방향: Hire [AI 1차 면접 보내기] → Screen 이 면접 한 건과 링크를 만든다(Hire 후보자 id 를 같이 적어 둔다) → 후보자는 Hire 메일로 링크를 받는다 → 끝나면 Hire 후보자 상세가 Screen 에서 **요약(종합 점수·문항별 등급·검토 상태·리포트 링크)** 을 읽어 온다. Screen 이 Hire 를 가리키므로 **Hire 쪽 표는 바꾸지 않는다.**

## 마일스톤

| | 이름 | 끝났다고 말할 수 있는 상태 |
| --- | --- | --- |
| **SC0** | 결정 3개 (사용자) | 아래 "정할 것" 3개에 답이 있다. |
| **SC1** | 서버 저장 (8단계) — 코드 완료, 표 만들기(사용자 SQL) 뒤 한 바퀴 확인 | 공고·평가 기준, 면접 링크, 대화, 점수, 담당자 검토가 브라우저가 아니라 Supabase 에 남는다. 다른 기기에서 같은 링크로 이어하기가 된다. 후보자 쪽으로 평가 기준이 내려가지 않는다(서버에서만 읽음). |
| **SC2** | 채점 AI (7단계 ①) | 후보자가 제출하면 서버가 Claude 로 문항마다 점수·근거 문장·이유를 만든다. **근거 문장은 답변 원문에 글자 그대로 있어야 저장**(없으면 버리고 "근거 확인 필요"). 쓴 모델과 규칙 버전을 같이 남긴다. 실패하면 "채점 대기" + [다시 채점]. |
| **SC3** | 후속 질문 AI (7단계 ②) | 지금의 "120자보다 짧으면 되묻기" 규칙을 Claude 판단으로 바꾼다. 정해 둔 횟수(0~3) 안에서만, 평가 기준 문장은 절대 후보자에게 안 보이게. AI 가 안 되면 지금 규칙으로 자동으로 돌아간다. |
| **SC4** | 한 계정 + Hire 연결 | 담당자 화면은 TalentCore 로그인(Core `/sso/screen`, Grow 와 같은 방식). Hire 후보자 상세에 [AI 1차 면접 보내기] 와 결과 요약 칸. 담당자 역할 제한은 Hire 규칙(HM·면접관은 자기 공고만)을 따른다. |
| **SC5** | 배포 + 운영 한 바퀴 | Vercel 에 Screen 을 올리고 로고(사람 칸 왼쪽 아래)를 붙인다. 연습 후보자 한 명으로 Hire 보내기 → 면접 → 채점 → 검토 → Hire 에서 보이기까지 한 바퀴. 테스트 기록 정리. |

순서 이유: 저장(SC1)이 없으면 채점 결과를 둘 곳이 없고, 채점(SC2)이 후속 질문(SC3)보다 먼저인 이유는 "무엇을 되물을지"가 채점 기준에서 나오기 때문이다. Hire 연결(SC4)은 Screen 혼자 한 바퀴가 돈 뒤에 붙인다.

## 정할 것 (SC0 — 사용자)

1. ✅ **확정(2026-09-24): Hire 와 같은 프로젝트에 `screen_` 로 시작하는 표.** (SQL `supabase/screen-001-tables.sql`) — 추천 이유: 키를 새로 만들 필요가 없고 Hire 가 요약을 읽기 쉽다. 표 만들기는 늘 그렇듯 붙여넣고 Run 하는 SQL 한 덩어리로 드린다.
2. **Claude 키** — 규칙상 **키는 제가 넣거나 연결하지 않습니다.** 사용자가 Vercel 환경변수 `ANTHROPIC_API_KEY` 에 직접 넣는다. 키가 없어도 Screen 은 돌아간다(채점은 "채점 대기", 후속 질문은 지금 규칙).
3. **모델·비용** — 면접 한 건에 Claude 호출이 약 (문항 수 × 후속 질문) + 채점 1회. 추천: 후속 질문은 빠른 모델, 채점은 가장 좋은 모델. 모델 이름은 코드에 박지 않고 설정값으로 둔다(지금 코드의 `claude-opus-5` 는 옛 이름이라 SC2 에서 같이 바꾼다).

## 저장할 표 (SC1 초안 — 실제 SQL 은 SC1 에서)

- `screen_jobs` — 공고(Hire 공고 id), 직무 설명, 질문·기준·비중 묶음
- `screen_interviews` — 추측 어려운 링크 토큰, Hire 후보자 id, 익명 라벨(후보자 A…), 상태(발급·진행·제출), 동의 시각, 만료
- `screen_messages` — 대화 한 줄씩(질문·답·후속 질문), 제출 후 수정 불가
- `screen_scores` — 문항별 AI 점수, 근거 문장, 이유, 모델, 규칙 버전
- `screen_reviews` — 담당자 수정 점수·메모·검토 상태(AI 점수는 덮어쓰지 않고 따로)

## V1 밖 (지금 안 한다)

- 음성·영상 면접, 말투·억양·표정 평가 — 설계 원칙상 평가하지 않는다
- AI 가 합불을 정하거나 점수순으로 줄 세우기 — 원칙상 하지 않는다
- 부정행위 감지(창 전환 추적 등), 다국어, 공고마다 다른 채점 모델
- 평가 기준 템플릿 공유 라이브러리

## 지켜야 할 것

- `ANTHROPIC_API_KEY` 는 커밋하지 않고, 제가 연결하지도 않는다. 키는 서버에만.
- Supabase 표 변경은 사용자에게 SQL 한 덩어리로.
- 후보자 화면에 평가 기준을 내려보내지 않는다. 점수에는 반드시 근거 원문이 붙는다.
- 직무와 무관한 개인 정보(나이·성별·가족·출신 등)는 질문에도 채점에도 쓰지 않는다.
